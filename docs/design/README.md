# Design principles

The project is developed following an AI first approach:

- Opus 4.7 (claude.ai) was used to drafted-up the design documentation.
- Sonnet 4.6 was the default implementation model (Claude Code), sometime
  supported by an Opus 4.7 advisor.

*Note: this document simply records the steps I followed while experimenting
with AI for software generation; it does not aim to present best practices, it
merely evaluate the subjective quality of the results obtained.*

## Design phase

**claude.ai (Opus 4.7)** I initialized a project from the claude.ai webapp,
with the instructions that the documentation should be generated in english and
that I'm completely oblivious to GPU constraints.

**claude.ai (Opus 4.7)** The first step was the technological choice:
C11/OpenCL, `cmake` build chain and `vcpkg` third party manager. C was a
conscious choice: I'm no C developper and have wanted to make C pet project for
some time. Choosing the rest of the stack (OpenCL, `cmake` and `vcpkg`) was
made using claude.ai. The very short trade-off:

- C11: widely implemented
- OpenCL: pure C, more generic than CUDA, higher level than Vulkan Compute
- `cmake` for a portable gcc/MSVC build
- `vcpkg` because it has a friction-free OpenCL port. Plus it seems to be the
  fotm C/C++ package manager for portable builds.

**Claude Code (Sonnet 4.6)** The following design step was to analyze the data
model powering the behavioral neural network of the original biosim4. I asked
Claude Code for a design document, with an emphasis on foreseen GPU constraints
(e.g. some behaviors are non-local: neighbors dependant and multi-level
heap-pointers indirection). The analysis can be found mostly unchanged in
[04-legacy-data-model.md](04-legacy-data-model.md)

**claude.ai (Opus 4.7)** This data model analysis was dropped into the project
files. I then asked claude.ai for a design document for the repository
structure. I specified that the structure should support:

- Design, build and usage documentation
- C source code for 2 versions of the simulator: a GPU accelerated simulator to
  power through the generations, and a drivable simulator for visualization.
- Unit test for the C source code
- It will be a mono-repo, with visualizers to come later

The discussion that followed yield the bulk of the design documents including
the SoA refactor and consumed most of my Pro weekly quota.

This phase roughly ends with the manual initialization of the repository,
copying the design documents in the structure.

## Transitioning to implementation

**Claude Code (Sonnet 4.6) and claude.ai (Sonnet 4.6)** The transition to
implementation was done back and forth between claude.ai and Claude Code to
finalize some lower impact design choice (e.g. implementation conventions,
toml/cli design ...) and refine build targets.

This phase starts with
[commit](https://github.com/Meuna/biosim4-gpu/tree/7674b1d9837517b6f6f9bb38cdb96dc2cba66b5b)
**"Add a first iteration CLAUDE.md as generated by /init"** and end with
[commit](https://github.com/Meuna/biosim4-gpu/tree/db5f8db05a44c15cd664bed693f1e855168b89db)
**"Create the source and build scaffold with a hello world and an empty test"**.

## Implementation phase

**Claude Code (Sonnet 4.6)** From there, most of the implementation was done
using Claude Code, following this approach:

- Plan the next logical steps, often suggested by Claude Code /recap. This
  aligned quite well with the design plans.
- Review the plan, maybe with follow-up questions/suggestions.
- Accept the plan with auto-accept edits.
- Review of the code generated, maybe with follow-up questions/suggestions.
- (5% of the time, usually to save on token) Manual edits. 60% are tests
  addition and 40% are documentation/design refinement. 0% code.
- (Optionally) Run the linter and formatter.
- (Optionally) Run the compilation and tests.
- Manual commit.
- Repeat.

## Impressions

The Opus 4.7 design choices seems perfectly justified. The success of the GPU
acceleration remains to be proved but for a GPU noob, the decisions are very
convincing.

With the design documents, Claude Code is mostly on auto-pilot. The very early
code files needed some adjustments, but as the code is growing and getting a
*personality*, I found that I have less and less to comment.

Most of my comments concern the headers and the tests, which is not surprising
as they scope the code architecture and behavior more than the code. To my
surprise, I have found that reviewing the tests is not too much of a chore: the
scope of the test file is daunting at first, but reviewing the first test make
me want to read the rest. To the contrary, I mostly scan through the code
looking for obvious issues and usually find none.

Accordingly, Claude Code is very verbose when documenting the headers but
scarcely document the sources.

The most painful parts are:

- getting Claude Code to keep the documentation aligned with the code,
- and getting Claude Code to reliably run the lint and format.

As a result, I find that managing CLAUDE.md and trying to keep is small is not
intuitive.

   refer to the sensors and actions. Arguably the largest commit at the time.
- **"Remove age attribute from agents structure"**: refactoring
- **"Implement feedforward in nnet"**: implement the sensor to action propagation.
  Medium to large commit.
- **"Assemble everything a simulation smoke test"**: simple main loop, medium commit.
